## Before Generating New Code

**Default to the smallest change that works, built out of code that already exists.** Both halves are load-bearing. This repo has repeatedly paid to *delete* layers that only forwarded a call — `db/stores/utils.py`, the parallel node dicts (`NODE_TYPE_TO_CLS`, `CATALOG_TIERS`, …), `preflight()`, `BookRecommendationOutput` — and each new one costs that removal again later.

**0. Start from the worked example, never from a blank file.** Two slices are the maintained templates, and every workflow in the app follows their shape: **`books/find_by_title/`** for a single-call node (parse args → build the query → count → preview → finalize), **`books/find_similar_books/`** for a multi-step node — `executor.py` is the flow with numbered steps, one satellite module per LLM call's pure half, `dependents.py` interprets upstream artifacts. Copy the matching one and edit; the layout, `@task` placement, request-builder convention (`build_*_request` as a module-level pure function) and the `finalize_result` claim are already decided there. The reading rule both follow is in `backend/app/domains/README.md`.

**1. Search before you write.** Before adding a function, model, constant or helper, grep for the one that already does it. The things that get reinvented most:

| Reaching for | Already exists |
|---|---|
| serialization, ids, timestamps, pricing | `airglider` — `to_serializable`, `remove_empty_values`, `strip_zero_token_usage`, `now_iso`, `uuid_8`, `cost_of`. `common/utils` **re-exports** these; never keep a second copy |
| counting / previewing / fetching / streaming books | `BookWorkflow` — `count_books`, `fetch_books`, `stream_books`, `self.store` |
| anything derivable from an already-built query | `DeferredBookQuery` — `count_stmt()`, `materialize_stmt()`, `compose()`, plus `compile_sql` |
| "which nodes exist / which executor / what's in the catalog" | `REGISTRY` — it answers from `SPECS` alone; never a module-level dict beside it |
| an LLM call from inside a node | `AppWorkflow.run_llm_args_parse` / `run_llm_tool_calls` |
| a book model with fewer fields | `Book` — narrow at the point of use (`model_dump(include=...)`), never a new class |
| a path, a limit, a model name | `config/constants.py` / `settings` — no literals at the call site |

**2. Take the smallest rung that fits.** The `@task` ladder in `backend/app/domains/README.md` (pure function → `run_llm_*` helper → `@task` method → full `Workflow`) is the specific case of a general rule: prefer a function to a class, a method on the object that already owns the data to a new module, a field to a subclass, a default to a flag. Add the next rung only when the current one demonstrably cannot carry the work.

**3. Don't build for a caller that doesn't exist.** No parameter with one value, no flag with one branch, no base class with one subclass, no "we'll need this later." `ParsedInput` is the standing example of the exception being *documented rather than spread*: it exists for PlanJane alone, and new slices are told not to pre-build it.

**4. Reuse means calling what exists — not hoisting new shared abstractions.** Some duplication here is deliberate and must survive: each slice writes its own `build_arg_parser_request` (so one node can change model or prompt without a flag on a shared base), `planjane/dial/` imports nothing from `app/`, and `airglider/` imports nothing from the app at all. Before factoring two things together, check that they are the same thing rather than two things that currently look alike — and that the merge doesn't cross one of those seams.

**5. Removal is part of the change.** If an edit makes a function, field, test or doc paragraph dead, delete it in the same change instead of leaving it for later; a codebase this size has no room for a deprecated tier. Say what you removed when you report the work.

## Files to Avoid Reading

To save tokens, do not read these unless the task specifically requires it:

- **Log files** (`backend/logs/` — `*.log` and chat-run JSON dumps): skip unless the task is formatting or restructuring the logs themselves.
- **SQL backups/dumps** (`backend/data/*.sql`, e.g. `backup.sql`; `backend/data/backup/`, e.g. the 67 MB `books.sql` seed; `backend/evals/results/**/*.sql` raw eval dumps): never read these. The schema init SQL in `backend/db/init/` (extensions/tables/indexes) is fine to read.
- **`backend/playground/app_mock/`** — **outdated, ignore.** The mock executors and extended node schemas were the stand-in used for eval testing before the slices had real executors. They are no longer maintained and nothing live reads them (`NodeSpec.executor` points at the real slice executors). Don't read them for context, don't update them alongside a change to the real code, and don't model new code on them.

If a file is in gitignore, you probably don't need to read it.
Ask for confirmation before reading large files

## Architecture

### Design: Request-Based Planning (not a static graph)

Instead of a fixed routing graph, this system uses **LLM-driven preplanning**: the user's message is turned into structured schema requests that an LLM fills out, producing an explicit task plan before any retrieval or analysis runs.

**Why:** New capabilities only require adding a tool schema — no graph rewiring. The preplanning step also produces a Mermaid diagram the user sees before execution, which aids debugging and builds trust.

**Tradeoff:** Two LLM calls (parse + classify) before real work starts. Acceptable for a chatbot where latency expectations are relaxed.

### Triage → PlanJane → TaskRunner

Three layers, one per question, each an `AppWorkflow` with its own envelope in the trace tree:

1. **`Triage`** (`app/orchestration/triage/`, `TriageWorkflow`) — decides *whether to plan at all*: replay a cached plan, turn the message away, or hand the planner the book part of it. After the cache and before the planner, a gpt-5-mini **query decomposition** (`QueryDecomposition`, 2026-09-24) splits the message into `QueryPortion`s — each one ask or remark in the user's own words, labelled `in_domain` / `small_talk` / `out_of_scope` / `security` / `gibberish`. `out_of_scope` is the clearly-not-a-book-app but harmless (essays, weather, trivia); `security` is only misuse (injection, internals, data changes); `small_talk` is only greetings and the basics (name, what it can do) — a deeper project question is `in_domain`. The planner is asked the `in_domain` portions only, joined in message order; the other portions are dropped (the reply writer still reads the whole message). A message with no `in_domain` portion gets one fixed reply from `REPLIES`, whose order is the priority (security, out of scope, small talk, gibberish), and ends the turn as ok with no plan, so nothing the decomposition model writes reaches the user directly. It is told to be loose on `in_domain` (misspelled, vague or unsupported book asks all pass; the planner decides what it can do) and lenient on `out_of_scope`/`security` — the user's own session, explanations of BookShelf's code, and follow-ups that relate to earlier turns all pass. The prompt reads earlier turns when it is given them, but nothing supplies them yet (single-turn), so a follow-up that cannot stand alone is `gibberish` today. It **fails open**: a split that errors sends the whole message to the planner. Laid out like a slice: `external.py` (`TriageOutput`, `QueryPortion`, `TriageVerdict`), `tools.py` (`QueryDecomposition`), `executor.py` (`TriageWorkflow`, `build_decomposition_request`, `REPLIES`), `cache.py` (the dev plan replay), `prompts/decompose_query.txt`. It lives in `orchestration/` rather than `domains/` because it is not a capability — no `NodeSpec` will ever point at it, and its only domain knowledge is which planner to call. It is a workflow rather than methods on `Orchestrator` because `Orchestrator` owns no envelope: folding it in would mean a cache hit or a refusal produced no step in the trace.
2. **`PlanJane`** (`app/domains/planjane/`, `PlanJaneExecutor`) — *the planner*. Sends the user message to the LLM with the whole tool catalog (descriptions come from docstrings on the node request-schema classes) and returns goals with ids. It also **owns plan presentation**, and is the only thing in the app that renders a Mermaid diagram at all: `send_mermaid` stamps it onto `PlanJaneOutput`. The whole stack lives in `planjane/dial/` — `mermaid.py` turns goals into `MermaidBox`es (what a box says, plus the `depends_on` → `sent_to` inversion), `format.py` turns boxes into the string (markup, orientation, emission). **`dial/` imports nothing from `app/`** — only `airglider`, which is itself standalone — because PlanJane is headed for being a service of its own, and this is the corner already free to travel. Keep it that way when editing. Split three ways, matching the slice layout used elsewhere: `external.py` (`SystemGoal`, `PlanJaneOutput`, `ExecutionOrder` — what the plan *is*, and what triage and the task runner import), `tools.py` (`GoalParseRequest`, `MAX_SYSTEM_GOALS` — what the LLM fills in), `executor.py` (`PlanJaneExecutor` — what runs). The dependency runs `external ← tools ← executor`; import from the `planjane` package root rather than any of the three.
3. **`TaskRunner`** (`app/orchestration/task_runner.py`) — executes the plan. Its input is `TaskRunnerInput(plan: PlanJaneOutput)` and nothing else — no `query`, because the plan drives all of it, and never a `TriageOutput`: the runner executes plans and should not know a triage layer exists. `Orchestrator` is the one place the two are wired together, which keeps that import pointing downward.

Each capability is a **vertical slice** — one folder under `app/domains/<domain>/<node>/` holding its label, its request/input/output schemas and its executor, exporting a single `NodeSpec` (`app/domains/node_spec.py`). The three schemas are distinguished by who fills them in: `request` by the planner LLM choosing the capability, `input` by the task runner assembling the planner's instruction and upstream outputs, `output` by the executor. (`request` and `input` converge eventually — the parsed args are an input the node currently produces for itself.) **The `request` the spec points at is fieldless** — a docstring and the `node_type` Literal, which is all the planner needs to pick a capability and write the goal's instruction; the arguments live on a separate plain-`BaseModel` `*Args` schema in the slice's `tools.py` (the request itself lives in `external.py` beside `input` and `output`) (`FilterRetrievalArgs`, `RecommendationArgs`), which is what the node's own parse call ships as its tool schema, what `run_llm_args_parse` returns, and what the output's `args` field is typed as. Those are **internal tools** like `IdealBookDescription` — never seen by the planner, so no `node_type`/`confidence`/`reasoning` and no place on the spec. See rule 1a in `backend/app/domains/README.md`. A domain's `guide.py` lists its specs; `app/registry.py` composes those into `SPECS` and hands that tuple to one **`Registry`** (`REGISTRY = Registry(SPECS)`). **The specs are the registry's only state**: it indexes them by `node_type` once, rejects duplicates, and answers everything else as a read over that index — `spec()` / `request()` / `executor()` / `executors()` / `in_tier()`, `node_type in REGISTRY`, `catalog_entries()` / `format_catalog()`, `node_type_enum`, `request_union()`. Lookups take a `NodeTypeEnum` member or a plain string, so no caller reaches for `.value`. The parallel module-level dicts are gone (`NODE_TYPE_TO_CLS`, `CATALOG_TIERS`, `RETRIEVAL_CLASSES`/`ANALYZE_CLASSES`/`REQUEST_CLASSES`, `AnyStrategyRequest`, `EXECUTORS_CLS_MAPPING`) — each rebuilt the same spec relationship from a different angle, which is how a node could be present in one and missing from another. Schemas describe *what* to do; **executors** (the *how*) subclass `AppWorkflow` and are reached through the spec. To see what the planner is actually told it can do at any moment, run `make tools-catalog` rather than trusting a checked-in snapshot: it renders the live registry.

**Adding a new capability:** see the step-by-step recipe **and the "Writing an executor — the rules" section** in `backend/app/domains/README.md` (new slice folder → request schema with LLM-facing docstring → `SPEC` → one line in the domain's `guide.py` → eval cases; the rules cover the parse → work → finalize body, the `@task` ladder, and the `finalize_result` claim). The planner picks it up automatically via the tool-loading step. The V1 node set is a settled decision: [docs/design/node-taxonomy-v1.md](docs/design/node-taxonomy-v1.md).

### Request Flow

1. **Frontend** sends a chat message via SSE to `POST /session/{id}/message`
2. **`Orchestrator`** (`app/orchestration/orchestrator.py`) — transport lifecycle only: SSE, timeouts, cancellation, recording. Builds a `RequestContext` and delegates to `TriageWorkflow`
3. **`Triage`** decides whether to plan, and calls **`PlanJane`** if so; the plan then travels to **`TaskRunner`** as an artifact
4. Results stream back to the client via **SSEStream** (`app/common/sse_stream.py`)

**Package layering is one-directional** and worth keeping that way: `app/common/` (messages, sse_stream, `RequestContext`) ← `app/domains/` (AppWorkflow, nodes, planjane) ← `app/orchestration/` (Orchestrator, Triage, run_recorder). `RequestContext` sits in `app/common/` because every layer reads it; it used to be in `app/orchestration/`, which made those two packages import each other.

**Current state:** `TaskRunnerWorkflow` (`app/orchestration/task_runner.py`) executes the classified strategies against the real executors, for the node types registered on this branch. It brackets each node with `task.start`/`task.end` SSE events so the UI can render one collapsible section per step (the goal's instruction and count in the header, then the step's details — parsed args, SQL, cost, which `task.end` carries — then its preview cards under a label); see `frontend/src/README.md`. **The turn's prose is written by an unregistered stage, not by the runner and not by a node** (deregistered 2026-09-08): `Orchestrator._write_reply` runs `GenerateRecommendationsExecutor` (`app/orchestration/write_recommendations/`) exactly once after the runner, over `TaskRunnerOutput.task_results` — every goal's output, not one chain's. Each goal arrives as a `TaskResult` (`app/orchestration/task_runner.py` — the node's output plus a summary of its envelope: duration, total/input/output tokens, error type and message; since 2026-09-11 the turn's source of truth). The stage fetches nothing: it writes from a report capped per goal — an `<info>` block (outcome, error message, arguments, cost, SQL) and up to four books from the `preview` each node already kept, each labelled with a handle (`1.2`: section 1, book 2). The reply comes back as structured blocks (`GenerationResult`: a text, then a source naming the handles of the books that text talks about), and the stage sends them in that order — so the answer reads paragraph, its cards, next paragraph, and only books the text points at are shown as cards in it. A crashed goal's error reaches the writer as its message only, and the prompt turns it into a plain cause ("that isn't something I can do yet"). **Every planned turn now gets prose**, which closes the old "a plain lookup gets cards and no prose" gap and costs the golden check that a *planned* generation goal gave. A goal that fails or is skipped leaves a typed `FailedGoalOutput` in that map (stamped, like every output, with its `goal_instruction`), which is what lets the stage say "I don't have Dune, so I couldn't line anything up against it" — only the *ancestor* knows why the chain stopped. This is the sink-shaped alternative from branch `generation_node_sink`, collapsed to one sink per turn; the comparison and the reversal are in [docs/design/execution-pipeline-v1.md](docs/design/execution-pipeline-v1.md). Conversation is **single-turn**: each request is processed statelessly (turns are recorded to `chat_runs` but never read back).

### API Surface

`GET /health` · `GET /ping` · `GET /ready` — health/readiness. `POST /session/new` — mints a session id, and persists nothing: the `sessions` row is created by the first message. `POST /session/{session_id}/message` — SSE chat, guarded by the session's token budget. **The route touches no database**: it validates the message, builds the `RequestContext` and hands the turn over. `Orchestrator.run` does all three budget steps itself — `start_session_turn` (a `@task`, the turn's first step, the round trip that also creates the row on a first message), then judging the balance, refusing a spent session with an SSE `error` event rather than a status code — the response is a stream, and the frontend renders any non-200 here as its own generic "something went wrong" — and finally the debit in `_finalize`, so a session goes one turn into the red rather than being cut off mid-turn. **Enforced in every environment since 2026-09-23**; the production-only gate (`token_budget.ENFORCED_IN`) is gone, so a `make dev` session or an eval suite stops when its 50,000 tokens do — `evals/planjane/run_suites.py` reuses one session per run, so a long suite needs a session per case or a larger `SESSION_TOKEN_BUDGET`. **Production also caps the site as a whole** (2026-09-24): the session id comes from the URL, so a made-up one starts with a full budget, and `run` therefore reads `read_site_spend` (every session active in the last 24h, as budget minus remaining) and refuses once it reaches `AppConfig.SITE_DAILY_TOKEN_BUDGET`; the chat route is also rate-limited per IP in memory (`limit_messages_per_ip`, `AppConfig.MESSAGES_PER_IP`, a 429). Both are production-only, so eval suites are untouched. `PUT /session/{session_id}/message/{chat_id}/feedback` — the chat's thumbs up/down and comments (`ChatFeedback`), served everywhere: it upserts the same `feedback` row a review would — `FeedbackIn` is `ReviewIn`'s body without the ids — keyed by the session that produced the run, and 404s unless `ChatRunStore.belongs_to` finds that run recorded under that session — so a session rates only what it asked, and a click before the turn's row lands is a 404 the UI reverts. (No row is recorded in development, so it always 404s under `make dev`; test it with `make local-prod`.) `GET /chat_runs` — review queue (least-reviewed first, and the chat's reactions count as reviews there); **it and the two review routes below are not served in production** (2026-09-24) until the admin gate lands — review locally with `make dev-neon`. `PUT /feedback/review` — upsert one review per (chat_id, session_id). `GET /feedback?chat_id=` — list reviews for a run. That is the whole surface — there is no `/add_feedback` and no `/chat_runs/tests`. No auth exists yet (pre-deploy blocker, docs/backlog.md). **Firebase App Check** (2026-09-24) guards every route but the three health checks: `require_app_check` (`app/api/dependencies.py`) verifies the `X-Firebase-AppCheck` header that `frontend/src/api.js` attaches, and is enforced only when `APP_FIREBASE_PROJECT_NUMBER` is set — the deploy recipe sets it, local dev doesn't. It proves a request came from the site, not who sent it: a token copied out of a browser replays with curl until it expires, so it is no substitute for the admin gate (docs/deployment.md §4.1).

### Workflow / Operation Pattern — the `airglider` library

**`backend/airglider/` is a separate project living in this repo** — a self-contained tracing/result library (extracted from the old `common/operation.py` + `common/workflow.py`) that will eventually be lifted out as its own distribution. **Read [backend/airglider/README.md](backend/airglider/README.md) before writing a `Workflow` or `@task`, or before editing anything under `airglider/`.** Its "The rules" section is the contract — instrumentation, `ok` semantics, the two step verbs, `StepFailure` — and it is not restated here, so this file cannot drift from it.

The four facts that concern *this app*:

- **Always import from the package root — `from airglider import OperationResult, Workflow, task`.** Never reach into `airglider.src.*`. `airglider/__init__.py` is the whole public surface; a symbol not re-exported there is not API (adding one means adding it to that file's `__all__`).
- **airglider imports nothing from the app**, which is what keeps it extractable — preserve that when editing. It therefore owns the serialization/identity helpers its record tree is built from (`to_serializable`, `remove_empty_values`, `strip_zero_token_usage`, `now_iso`, `uuid_8`) and the model price table (`airglider/src/config.py`, moved from the old `config/pricing.py`). `common/utils` **re-exports** those helpers rather than keeping a second copy, so importing from either place gets the same function.
- **Its tests live in `airglider/tests/`**, not under `tests/` — `make tests-airglider`, folded into `make tests-all`.
- **`BaseLLMRequest.to_summary()` (`clients/base.py`) exists because of `record.input`.** Every unit of work stamps its arguments before running, and a value's own `to_summary()` wins over a full dump — so without that method every prompt and message list would land in `chat_runs`, which is exactly what `save_payload` already gates. Give any large payload a `to_summary()` and it collapses everywhere at once.
- **`clients/` is tracing-free** — headed for standalone like airglider, so no `@task` lives there: client methods raise and return payloads, and `AppWorkflow`'s thin wrappers (`llm_execute`, `get_embeddings`, `execute_tool_call`) are where a client call becomes a step, gets its failure captured, and has its `token_usage` promoted. Its one airglider import is the `TokenUsage` data shape (fine — airglider is standalone too); the one remaining app import is `SSEStream` on `BaseLLMRequest`, the known last coupling (see the TODO in `clients/base.py`).

The app's own layer on top is `AppWorkflow` (`app/domains/base_workflow.py`), which adds SSE helpers and `finalize_result(ok=…)`; see the naming ladder under Domain / Node Type System below.

### Domain / Node Type System

`app/domains/` defines what the system can do:

- **The book node set.** The V1 taxonomy is `Retrieve_by_ISBN13`, `Retrieve_by_Title`, `Retrieve_by_Author`, `Retrieve_by_CoAuthors`, `Retrieve_by_Lexical_Traits` (renamed from `Retrieve_by_Category` 2026-08-24), `Retrieve_by_Numeric_Traits`, `Retrieve_Random`, `Combine_Union`, `Combine_Intersect` (replaced `Filter_Retrieval` 2026-08-24), `Analyze_Compare`, `Analyze_Similar_Books` (renamed from `Analyze_Recommend` 2026-08-22). `Generate_Recommendations` was registered 2026-09-07 and deregistered 2026-09-08 — writing the reply is no longer a capability the planner picks, and `NodeTier.GENERATE` went with it. **Six are registered** — the four retrieval nodes `Retrieve_by_Title`, `Retrieve_by_Author`, `Retrieve_by_Lexical_Traits`, `Retrieve_by_Numeric_Traits`, plus `Analyze_Similar_Books` and `Combine_Intersect` — so the rules below describe the target taxonomy, not what the planner can currently emit. `Filter_Retrieval` was **deleted** 2026-08-24 and replaced by `Combine_Intersect`, which unparks `NodeTier.COMBINE`; `Combine_Union` is still absent, so pooling stays implicit. `make tools-catalog` prints what is actually live. Each retrieval node is single-dimension (no cross-column filtering) and single-valued — one title, one author per node; several authors' separate bibliographies means several `Retrieve_by_Author` nodes. **Two nodes are documented exceptions on *dimension*, both because their subject has no single dimension to be single about.** `Retrieve_by_Numeric_Traits` carries a whole `BookMetadataFilter`, so bounds are always the **subject** of a search ("books under 200 pages", "well rated books"). **The numbers-only rule is retired (2026-08-24)**: a bound riding alongside another subject is this node *plus* `Combine_Intersect`, not a second parse inside a filter node, which is what let `Filter_Retrieval` and `BookStore.filter_query` be deleted together. The trap the rule used to guard is still live and now sits in this node's docstring: emitting the bound beside the subject and *omitting* the intersect pools them (OR) and answers with more books, not fewer. `Retrieve_by_Lexical_Traits` carries subject keywords + fiction-ness + audience, ANDed, because "non-fiction about history" is one question rather than two to intersect; it is the node for **anything that is not a number and not an identifier**. Its line against `Analyze_Similar_Books` is mechanism, not subject matter: `Retrieve_by_Lexical_Traits` is **lexical** (does the catalog's text contain these words — a tsquery over title + shelf + blurb, handing on a composable query over the whole match), `Analyze_Similar_Books` is **semantic** (which books are near an embedding — a ranked pool for a later step to pick from). They no longer split a single ask between them, though: the similarity node takes only named books, so "cozy mysteries" is `Retrieve_by_Lexical_Traits` alone with the feel dropped, not lexical + semantics. Note `genre` there means only fiction/non-fiction, the two values `books.genre` distinguishes; every finer shelf word ("mystery", "history") is a keyword. `Retrieve_by_CoAuthors` is the one multi-value node and means joint works only (2+ authors ANDed onto the same book), not a combined bibliography — see [docs/design/node-taxonomy-v1.md](docs/design/node-taxonomy-v1.md). `Retrieve_Random` is the one node that carries a full `BooksFilter` (a random pick has no dimension to be single about); it serves the bare "recommend me a book" **alone**, with no analyze node after it, and `Combine_Intersect` may never depend on it — bounds on a surprise go in its own `filters`. Cross-dimension requests are expressed by composition instead: the **combine tier** (`NodeTier.COMBINE`: `Combine_Intersect` = AND, and `Combine_Union` = OR when it exists) consumes prior retrieval output and searches for nothing of its own — it can only shrink or merge what earlier goals found. Under counts-first that is still SQL: `Combine_Intersect` ANDs the upstream *queries* together (`DeferredBookQuery.compose(op="and")`) and counts the intersection, rather than deleting from rows someone fetched. It takes 2+ dependencies of any book-producing shape — **how a set was found stops mattering once it is a set** — which is why one goal serves "horror by King over 500 pages" (three inputs) instead of an intersect followed by a filter. Pooling is also implicit — several task ids in one `depends_on` are pooled (OR) by definition — so `Combine_Union` is only used when that pooled set is an explicit step something downstream consumes — see [docs/design/execution-pipeline-v1.md](docs/design/execution-pipeline-v1.md). There is no generate tier: the plan covers *finding books* and nothing else, and the reply is written after every goal has run (see the Request Flow section). Siblings for book QA and compare, if they arrive, are branches inside the one reply prompt rather than slices of a tier. This domain's specs are listed in `app/domains/books/guide.py`; `app/registry.py` composes it with the other domains.
- **`NodeTypeEnum`** — the flat enum of every registered capability name plus `unknown`, built once in `Registry.__init__` and re-exported at module level as `NodeTypeEnum = REGISTRY.node_type_enum`. It stays module-level because it is a *type*: `SystemGoal.target_node_type` is annotated with it at class-definition time, which is also why the registry builds it once rather than per call. It is the constraint the planner LLM emits under. `unknown` is a member on purpose: it lets the model decline rather than pick a wrong capability, and `planjane/executor.py` refuses that goal with a reason instead of failing the whole tool call.
- **Shared output shapes** — `app/domains/books/external.py` (`BookRetrievalOutput`, `BookRequestContext`), over `Book` and the shape vocabulary in `app/domains/books/schemas.py`. `external.py` is what the layers outside the domain import, and is why a downstream node's `NodeInput` can declare `list[BookRetrievalOutput]` without reaching into a slice. A node's own output subclasses the shape its docstring claims in `Returns:`; `BookRecommendationOutput` is gone — the similarity slice subclasses `BookCandidateOutput` directly and adds the one field that shape does not have. **`BookRetrievalOutput` carries `num_books` + `query`, plus the section's `preview` rows** (kept since 2026-09-11): a retrieval node counts and hands on the query, and a downstream node composes against that — `preview` is the first `default_limit` rows the node already fetched for its cards, kept for the turn's record and the reply, and never an input. **Every registered node fills `query`** since 2026-08-24. `Analyze_Similar_Books` used to be the exception, declaring its own `books` field for a pool it had already fetched; it hands on a `score`-carrying `DeferredBookQuery` instead, which is what lets `Combine_Intersect` bound a similarity pool *with cosine order intact* (see the `db/stores` bullet). **It splits in two by whether the match can be anchored on** (2026-08-22): `BookAnchorOutput` for books the user *named* (`Retrieve_by_Title`, and `Retrieve_by_ISBN13` when it exists) and `BookCandidateOutput` for books matching a *description* (`Retrieve_by_Author`, `Retrieve_by_Lexical_Traits`, `Retrieve_by_Numeric_Traits`, and `Analyze_Similar_Books`' chosen pool, whose description the system wrote — which is what stops one similarity search anchoring the next). Neither adds a field — `build_input` fills by `isinstance`, so the type *is* the payload, and a node declaring `list[BookAnchorOutput]` structurally cannot be handed a 358-book subject search. The base stays concrete on purpose: it is what a node takes when it accepts *either* (`CombineIntersectInput` does), and what `CombineIntersectOutput` subclasses rather than picking a side at class-definition time — an intersection of two titles is anchor-shaped and one of two subject searches is not, so landing on the base means "not anchorable" and `Analyze_Similar_Books` cannot depend on it; `list[BookAnchorOutput | BookCandidateOutput]` is the *stricter* way to take both. Don't reach for a pydantic discriminated union — `_resolve` calls `isinstance` and a subscripted generic raises. `Book` is the single book model — every `books` column except `embedding` — and stays that way on purpose: narrow at the point of use (a prompt renderer picking fields, `model_dump(include=...)`), never by declaring a smaller model.
- **Domain base workflow** — `app/domains/books/base_workflow.py` (`BookWorkflow`), one layer under the domain-agnostic `AppWorkflow` (`app/domains/base_workflow.py`).
- **One call shape — `run(node_input)`.** Every unit of work in the app takes one argument: its own `WorkflowInput` subclass (`app/domains/node_input.py`). A node declares that class and lists it on `NodeSpec.input`; the task runner assembles it with `build_input(spec.input, goal.instruction, dependency_outputs)`. **`NodeInput.instruction` is the node's whole brief** (renamed from `query` 2026-09-07, along with `SystemGoal.description` → `instruction` and `NodeWorkflowOutput.goal_description` → `goal_instruction`): no node reads `ctx.user_message`, so the planner's line is the only thing it is told about the ask, and each slice ships it to its argument parser as an `AssistantMessage` — planner work, not a user turn. The reply stage is the sole exception and is not a node: it answers the turn, so the user's message *is* its brief. That makes it a self-containment contract on the planner rather than a label for humans: carry every literal the node needs, carry no other goal's work, resolve every pronoun (`docs/design/planner-shape.md`). Its bound is `MAX_INSTRUCTION_LENGTH` (300) and not `reasoning`'s `MAX_STRING_LENGTH` (100) because `bounded_string` truncates *silently* — a clipped label costs nothing, a clipped instruction changes what the node does. At the top of a turn the same field carries the user's own message (`Orchestrator` → `Triage` → `PlanJane`). **The declaration is the point, not the typing.** It replaced `(query, artifacts: dict[str, Any])`, which could tell a node something was missing but never *what* — so a node short of a dependency could only raise. A named, visibly unfilled slot says which one is empty and what shape would fill it — the seam an agentic node needs to ask the planner for one. Default a field whenever the node has a real fallback; require it only when the node cannot proceed, which for a list means `Field(..., min_length=1)` (`SimilarBooksInput.anchors`, `FilterRetrievalInput.anchors`) because an empty list is still a *filled* field. **Fields are filled by type, never by key** — `X` takes the first match, `X | None` takes it or None, `list[X]` takes all; keys are provenance. A required field that matches nothing raises `ValidationError` *naming the field*, which `TaskRunnerWorkflow._prepare` turns into one skipped goal. **Services are not constructor arguments and are not on the input** — `AppWorkflow.__init__(ctx, messages)` is the only `__init__` in the app layer, and `sse_stream`/`llm_client`/`app_env`/`session_id`/`user_message` are properties off the `RequestContext`. Context and input split on lifetime: services are built once per HTTP request, an input per dispatch.
- **A unit of work opens its own database session, and `RequestContext` carries only the factory** (2026-09-23). `ctx.store(BookStore)` is an async context manager over `session_factory.begin()`: it yields the store, then commits and closes. Per use, not per request, because the turn runs *after* the HTTP handler returns — FastAPI exits yield-dependencies at that point, which for the SSE chat route is before the first event is sent, so a store parked on the context would spend the whole turn on a session that was already closed. It is also what lets `Orchestrator._finalize` write inside its `asyncio.shield`. Two rules follow: **keep the block around the round trip and nothing else** (it holds a pooled connection and an open transaction while entered, and building a query needs no store — the builders are module-level functions), and **no store commits for itself** (the block owns the transaction; committing inside closes it early and the next statement raises). The plain HTTP routes keep a request-scoped session via `get_sqlalchemy_session`, now also a `.begin()` block, because there the request *is* the unit of work. This replaced `NodeSpec.context`, `RequestContext.stores`, `require_store()` and `BookRequestContext.narrow()` — machinery that resolved one store for one domain at dispatch, and only existed because the store had to be built earlier than it was used.
- **Naming (`Workflow` / `Executor`)** — the ladder is `airglider.Workflow` → `AppWorkflow` (`app/domains/base_workflow.py`) → `BookReaderWorkflow` → `BookWorkflow` (both `app/domains/books/base_workflow.py`). Concrete units of work are `*Workflow` too (`TriageWorkflow`, `TaskRunnerWorkflow`). **`Executor` is the subset of those the planner can dispatch** — a node with a request schema, a `NodeSpec` and a catalog entry, reached via `REGISTRY.spec(...).executor` instead of called directly. Node vs. pipeline step is what the second word carries. (The old "`Base` marks a reusable base class" rule is retired — see `backend/app/domains/README.md`.) **The last two rungs split on whether the output is book-shaped**: `BookReaderWorkflow` holds `store`/`fetch_books`/`stream_books`, none of which writes an output field, so it is bound to `NodeWorkflowOutput`; `BookWorkflow` adds `count_books`, which writes `query`/`query_sql`/`num_books`, so it is bound to `BookRetrievalOutput`. Every book-producing node subclasses the latter; `GenerateRecommendationsExecutor` is the one subclass of the reader alone, because it streams cards while producing prose. `BookWorkflow` carries `count_books(query)` and `fetch_books(query, limit)` — both `@task`s: the first stamps `query`/`query_sql`/`num_books` on the output and fetches nothing, the second hands rows back for the caller to place (a preview to stream and keep on the output as `preview`, or a capped anchor to keep) — plus `stream_books()`, which validates through `BookOut` before anything reaches the browser. There is deliberately no third: a node needing more composes it in its own flow, which is what replaced `fetch_anchor_books()` and its single caller. The counting/fetching pair replaced a single `preflight()` that returned `(total, sample)` from one round trip; splitting them made fetching a visible decision at the call site, which is why the rows a node keeps land on a field named `preview` rather than one that reads as its answer.
- `app/registry.py` — `Registry` answers every node lookup from `SPECS` alone

### Database

- **PostgreSQL + pgvector** via async SQLAlchemy (`db/async_engine.py`)
- Schema SQL in `db/init/` (extensions → tables → indexes) — mounted by Docker Compose locally, applied to Neon by `make neon-bootstrap`, never read by the app and excluded from the image along with `db/commands/` (ad-hoc queries and dated migrations)
- SQLAlchemy models in `db/schema/models.py`
- **The app writes to two tables live: `sessions` and `chat_runs`.** `sessions` (added 2026-09-22): `session_id` plus `remaining_tokens`, seeded from `AppConfig.SESSION_TOKEN_BUDGET` (50,000) on a session's first message and debited once per turn by `app/orchestration/token_budget.py` with the turn's whole spend — planner, tasks and reply together, read off the orchestrator's root envelope. `SessionStore.debit` subtracts **in SQL**, because two turns overlapping in one session hold separate `AsyncSession`s and a read-modify-write would lose one; it runs through `ctx.store(SessionStore)` like any other write, which matters here because `_finalize` is shielded and outlives the request. The *read* runs through the same door: `start_session_turn` is a `@task` in `token_budget.py`, called as the turn's first step and attached to its root with `add_step` (`run` builds that root rather than being a unit of work itself, so nothing is in scope to adopt it). `run` unwraps it, so a balance that cannot be read stops the turn instead of letting it spend against a number nobody saw. It ran in the route until 2026-09-23, which was the last thing keeping a database session open at the request boundary on the turn's behalf. `chat_runs` is the second live write, turned on 2026-09-23: `run_recorder.py` picks **one sink per environment** — production inserts a row through `ctx.store(ChatRunStore)`, development writes its JSON files under `logs/<chat_id>/`, test writes nothing — rather than returning early for everything but development. The two sinks are chosen in one place and wrapped in one `try`, because the rule is the same for both: recording never costs the user their reply. Note this landed ahead of the admin gate (docs/deployment.md §4.1), so `GET /chat_runs` now serves real user messages unauthenticated
- Repository pattern in `db/stores/` — `book_store.py` is the primary store. **Every statement goes through `BaseStore.execute_statement`**, which is the one place the compiled-SQL DEBUG log lives; a store method that calls `self.session.execute` itself bypasses it, and `tests/unit/db/stores/test_base_store.py` fails if one does — as it does if one calls `self.session.commit`. The `AppConfig.DATABASE_TIMEOUT` ceiling used to be here as an `asyncio.wait_for` and **moved to the engine 2026-09-23**: cancelling the await left the connection in a state SQLAlchemy no longer knew while Postgres kept running the query, so the constant now drives four layers, each above the one it backs up: `statement_timeout` (the server's own cancel — a `DBAPIError` with sqlstate 57014, connection still usable), asyncpg's `command_timeout` above it (a connection that never reaches the server), and `pool_timeout` plus asyncpg's connect `timeout` (the wait for a connection and the wait to open one, the parts Postgres cannot see — asyncpg's own default for the latter is 60s). `Orchestrator.DEBIT_TOKENS_TIMEOUT` is one rung further out again, since a debit pays those waits *before* its statement; level with `DATABASE_TIMEOUT` it would cancel a charge that was about to succeed. Retrieval is **counts-first**: `title_query()` builds a `DeferredBookQuery` that isn't run for rows, `count()` runs only a `COUNT`, `DeferredBookQuery.compose()` folds several into one CTE, and `materialize()` is the single place rows are fetched — each node's capped `preview`, and the similarity node's anchors. (`filter_query()` was deleted 2026-08-24 with `Filter_Retrieval`: a bound is `numeric_traits_query()` composed with the subject, so there is one way to narrow rather than two.) Statement derivation lives on `DeferredBookQuery` itself; **the builders are module-level pure functions and `BookStore` is only the execute half** (`count`/`score_stats`/`materialize`), so building, recording and composing a query never checks out a connection. `embedding_search_stmt` was the documented exception to that before 2026-09-23 — only its caller knows the label that elides its 1024-float vector from the recorded SQL — and the exception became the rule; keeping the build step out of the store is also what keeps airglider out of `db/`. **`DeferredBookQuery` carries no LIMIT and no ORDER BY — with one documented exception** (2026-08-24): the vector search keeps both, because it does not select a subset but orders the whole table and truncates, so the cap *is* the pool. `score_stats()` is its counting call, since `count()` on it only ever reports the LIMIT. **Nothing on the class marks the exception and `compose()` does not refuse it** — a `capped` attribute and a compose guard were built and removed the same day. What that leaves unprotected split in two on 2026-08-24: **`compose(op="and")` carries the one `score` through** (an intersect result is a subset of every input, so that column is defined on every output row), which is what makes `Combine_Intersect` able to bound a similarity pool *without flattening cosine order* — the LIMIT still applies first, so the count means "of the 250 nearest, N also match". **`compose(op="or")` still drops it and is still lossy** — a union contains rows the pool never matched — so tune `MIN_SIMILARITY` to bound the pool or restore the guard before registering `Combine_Union`. See `db/README.md` and [docs/design/execution-pipeline-v1.md](docs/design/execution-pipeline-v1.md)
- `db/ingestion/` populates books from `data/books.csv` — **legacy, ignore**: still uses old `Workflow`/`@task` patterns and will be reworked later; don't refactor it or model new code on it
